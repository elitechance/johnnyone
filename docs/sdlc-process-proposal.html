JohnnyOne · SDLC process proposal

Verify, don't trust

One initiative ran end to end through J1 — planned by claude, built by grok, validated by claude. It shipped. But the way it nearly didn't points at a single flaw in the loop, and the evidence for it is unusually specific.

11 phases 17 planning rounds 37 development review rounds 16 findings logged 8 distinct false passes

Every gate that accepted a self-report produced a false pass

Not sometimes. Every one. Wherever the coordinator asked an agent whether its own work was done and believed the answer, the answer was eventually wrong — and the run advanced anyway.

This is not a grok problem, and it is not fixable by better prompt wording. An agent reporting on its own work is the least reliable observer available, and the loop was built to ask it anyway.

Eight ways a green pipeline reported success on work that wasn't done

Worth separating, because they need different countermeasures — and only three can be automated away. The rest need a reviewer that reasons about what should be true.

The proposed process

Nine changes. Each one is traceable to something that actually went wrong, and each names the mechanism rather than the intention.

01

Every gate is a check the coordinator runs

Replace each "did you…?" with a measurement. The agent's report becomes a request to be checked, not evidence.

Mechanism Plan ready → overview.md + non-empty phases/ exist in the store. Phase ready → declared test_commands run from the workspace, gate on exit code. Tasks done → reconcile status.yml against the tree. Any mismatch bounces back with the evidence, and never advances.

Two of these now ship. The third is the last self-report still taken on faith.

02

The record must come from the run, not the agent

Numbers, screenshots and failure labels are all evidence, and all were wrong at least once.

Mechanism Test counts are written by the coordinator's own run. Screenshots record how the state was reached — route plus fixture — so a capture of the wrong state is visible without opening it. Identical image hashes across two inventory rows is an error. "Flake" requires a reproduction count or a linked issue; otherwise it is a defect or a required spec change and must be named as one.
03

Only blocking findings block

Lenses already self-label [blocking], [minor], "not a finding". That signal was collected and then discarded by a three-value verdict.

Mechanism Add PASS_WITH_FOLLOWUPS. Gate on blocking findings only; everything else lands in a follow-ups file that ships with the phase.

One round returned NEEDS_CHANGES with zero of ten findings marked blocking, having explicitly recorded the phase shape as "checked and accepted".

04

Converge on findings, not on a round counter

A large plan has an unbounded supply of refinements. Counting rounds measures patience, not readiness.

Mechanism Diff findings between rounds. If round N is disjoint from N−1 and none are blocking, that is convergence by exhaustion — advance. The round cap becomes a backstop rather than the mechanism.

Planning took 17 rounds; the last several were documentation. Development took 37 across 10 phases, and one phase oscillated 23 → 5 → 25 findings on evidence alone.

05

Immutable inputs are out of scope for findings

If a reviewer can demand changes to something the builder is forbidden to touch, the loop cannot close by construction.

Mechanism Mark inputs immutable explicitly. A gap in a locked mock is a note, never a NEEDS_CHANGES. Provide one register where undrawn states are recorded against an existing source of truth, and sweep it once, comprehensively.
06

Acceptance criteria must be executable

The single highest-leverage thing in the whole plan. Criteria written as commands can be checked by anyone in seconds; criteria written as prose produce debate.

Mechanism Require each acceptance line to be a command with an expected result — grep -rn "auxExistsFor" src shows exactly one definition and three consumers. Reject phases whose criteria cannot be evaluated mechanically.

Six greppable criteria let the whole first phase be verified independently in under a minute.

07

Test strength is itself a gate

"Tests pass" is satisfiable by editing the test. Pair it with "tests were not weakened".

Mechanism On ready, diff the spec files against the base: flag added force flags, removed assertions and downgraded locators. Add invariants the suite cannot satisfy vacuously — a selector named in a negative assertion must still exist in src; a content-visibility assertion must assert real geometry.
08

Force the unknowns before the code

The riskiest phase in the run opened with a section titled "Known unknown — resolve in task 01 before building", and it went smoothly. The phase that skipped that step spent five rounds discovering its own mechanism was wrong.

Mechanism Every phase touching an unfamiliar subsystem declares its unknowns as task 01. Decisions that belong to a human are surfaced as named gates before the phase starts, not discovered mid-implementation.
09

The loop must survive improving itself

Every fix in this list required rebuilding the binary that hosts the coordinator, which kills any run in flight — and planning runs land in a state that does not auto-resume.

Mechanism Move the coordinator out of process, or let it hand off and resume across a binary swap. Until then, "improve J1" and "run an initiative" are mutually exclusive, and improvements queue behind whatever is running.

What already works — keep it

The single highest-value property

Cross-model validation. The model that writes a workaround is the worst possible judge of it, because it looked reasonable when written. A different model, handed the acceptance criteria and told to verify rather than finish, went to elementFromPoint and real click trials instead of trusting the suite.

Three regressions this run were caught by measuring or experimenting, not by reading: a chat pane squeezed to 41px, a composer blocked by a bookkeeping await (proved by commenting out the call and re-running), and a SQL join that silently returned zero unread for anyone who had never opened a room.

Automation would have caught none of those three.

  • The reviewer refusing the builder's evidence. By the later phases it was re-running tsc, the suites and the schema gate itself, and saying so: "validated independently, not taken from the developer's artifacts".
  • Asking for the test that would have caught it, once established that the current suite could not. That is what turns a fix into a closed gap.
  • Naming decisions that belong to a human and refusing to guess — four product-owner gates were surfaced during planning rather than invented.
